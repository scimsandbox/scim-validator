# RFC 7644 (SCIM Protocol) coverage audit of the scim-validator suite

Scope: current repo state at `/Users/eduardpal/work/scim2/scim-validator` (matrix `SCIM_SPEC_COVERAGE.md`, tracker `SCIM_VALIDATOR_ASSESSMENT.md`, tests `src/main/groovy/.../specs/A1..A9`, base `base/ScimBaseSpec.groovy`). Primary spec text: RFC 7644 (rfc-editor text), RFC 7643, errata pages, and the two RFCs that update 7644.

## Q1. Does each matrix row match reality when the cited test is inspected at its file:line? Which statuses are wrong?

### Takeaway
Most RFC 7644 matrix rows and test line references are accurate, but there are seven material errors: (1) the matrix (and tests) swap RFC §3.5.2.2 (Remove) and §3.5.2.3 (Replace); (2) the "§3.1 Creating Resources" heading is the wrong RFC number (§3.1 is Background; creating is §3.3); (3) descending sort is marked Covered but the test passes when the server ignores `sortOrder=descending`; (4) the §3.1 Content-Location row cites RFC 7644 §3.1, but Content-Location exists only in RFC 7643 §3.1; (5) the §2 row's 403-tolerance note names SEC_09/SEC_12, which never test 403; (6) the §3.7 note "bulkId echo not asserted" is wrong — BLK_01 fails if the response omits `bulkId`; (7) the matrix's claim that A5 comments cite non-existent `§3.4.2.2.x` subsections is not true of the current code. All citable line refs in the RFC 7644 portion of the matrix were checked and are correct except those named below; the tracker (assessment) has stale line refs throughout A3/A4/A5/A6.

#### §3.1 Creating Resources (POST) — heading and Content-Location row are wrong; statuses otherwise right
- **Heading error**: the matrix heading "### §3.1 Creating Resources (POST)" mislabels the RFC ([SCIM_SPEC_COVERAGE.md:59](file:///Users/eduardpal/work/scim2/scim-validator/SCIM_SPEC_COVERAGE.md)). RFC 7644 §3.1 is "Background" (media type, message schemas); creating resources is §3.3 ([RFC 7644 §3.3](https://www.rfc-editor.org/rfc/rfc7644.txt)). The rows under the heading do use §3.3 correctly.
- Row "Content type `application/scim+json`; `Content-Location` on resource responses — Covered — SEC_04 A8:99, SEC_11–14 A8:217/232/250/274" splits two different specs: media type is RFC 7644 §3.8/[§8.1](https://www.rfc-editor.org/rfc/rfc7644.txt), and `Content-Location` does not appear anywhere in RFC 7644 (repo-wide grep of the RFC text finds zero occurrences). The requirement is RFC 7643 §3.1 `meta.location`: "This value MUST be the same as the 'Content-Location' HTTP response header" ([RFC 7643 §3.1](https://www.rfc-editor.org/rfc/rfc7643.txt), line 928). Test comments at [A8:218](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A8_SecurityAndRobustnessSpec.groovy#L218), [A8:233](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A8_SecurityAndRobustnessSpec.groovy#L233) and the section header on SEC_12 cite "RFC 7644 §3.1"; that attribution is wrong.
- Row "readOnly attributes supplied by client SHALL be ignored — Gap" is correct for POST: no test posts a client-supplied `id`/`meta` (verified against all POST payload builders, [ScimBaseSpec.groovy:297-391](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/base/ScimBaseSpec.groovy#L297)).
- Rows "201 + Location + representation + meta.resourceType" (USR_01 A3:30, GRP_01 A6:41) and "duplicate → 409 + uniqueness" (USR_13 A3:366, NEG_01 A9:39) are accurate. Under the matrix's own legend ("Partial — loose/conditional assertions"), the §3.12 `scimType` rows marked Covered should be Partial (matrix flags "Soft" in each note, so the status/legend are internally inconsistent).

## Q2. Which RFC 7644 requirements are missing entirely from the matrix?

### Takeaway
Beyond the Gap rows already listed, at least fifteen normative RFC 7644 requirements have **no matrix row at all**: the §3.1 ban on discovering message schemas; §3.2/Table 1–2 endpoint-method rules including "PUT MUST NOT create"; §3.3 null/`[]` clearing; §3.4 default returned-set semantics; §3.4.2.2 defaulted-attribute comparison; §3.4.2.3 missing-data ordering and multi-valued primary sort as first-class rows; §3.4.2.4 REQUIRED-ness of pagination fields; §3.5.2 `value` required for add, exactly-one-`op`, `primary:true` auto-unset, 204 branch, PATCH `attributes`-param-200; §3.6/§3.14 If-Match on DELETE; §3.7 `bulkId` REQUIRED on POST, per-op `version`, mandatory continue-after-partial-failure, §3.7.3 status/code prose; §3.8 UTF-8/default media type; §3.12 error body on 401; §4 single-object shape for `/Schemas/{id}`; plus the optional-feature hygiene rules (PATCH/ETag/filter gating) and the RFC 9865/9967 updates.

### Cited Findings
1. **§3.1 message schemas not discoverable**: "SCIM message schemas using the above prefix URN SHALL NOT be discoverable using the '/Schemas' endpoint" ([RFC 7644 §3.1](https://www.rfc-editor.org/rfc/rfc7644.txt)). No test checks that ListResponse/PatchOp/Error/SearchRequest schemas are absent from `/Schemas`; A1:146 only looks for the User schema. No matrix row.
2. **§3.2 Table 1/Table 2 endpoint-method rules**: Table 1 defines GET/POST/PUT/PATCH/DELETE semantics and states "PUT MUST NOT be used to create new resources"; Table 2 maps `/Users`, `/Groups`, `/Me` (GET, POST, PUT, PATCH, DELETE), `/Bulk` (POST) and `[prefix]/.search` (POST). There is no §3.2 matrix row; PUT-not-create is only incidentally tested (USR_15 A3:447, GRP_10 A6:258) and `/Me`'s non-GET verbs are untested.

MAY specify 'null' for a single-valued attribute or an empty array '[]' for a multi-valued attribute to clear all values" ([RFC 7644 §3.3](https://www.rfc-editor.org/rfc/rfc7644.txt); same text in §3.5.1). The matrix's single ListResponse row does not state these; no test asserts `Resources` presence as a contract or negative values in response fields.

### Inferences
- The five originally suspected comments are not isolated typos: they follow a pattern where the author summarized remembered behavior from the pre-RFC SCIM drafts/OpenSearch and then wrapped it in quotation marks. Any audit that trusts test comments as RFC quotations will overstate compliance.
- FLT_33/FLT_35/FLT_36 are the three tests whose *assertion* is also affected: FLT_33's 501 tolerance is harmless but its missing root-scoping check hides a real gap; FLT_35 is substantively correct despite the quote; FLT_36 and A1:222 assert beyond the RFC and can fail compliant servers.

### Gaps
- I could not determine whether earlier versions of the repo cited `§3.4.2.2.x` subsections (the matrix's claim); git history for the untracked docs/tests was not available (`SCIM_SPEC_COVERAGE.md` is untracked per `git status`), so this is judged only from the current tree.

## Q4. Do any RFC 7644 errata (or updates) change these interpretations?

### Takeaway
Yes, four errata are directly relevant — 6893 (the §7.5.2 example's `status` is 403, not 404), 7916 (the §3.7.3 bulk error example is repaired, but the prose-vs-example `status` object/string conflict remains and the suite assumes a string), 7319/7322 (the `not (` spacing in the filter ABNF, which FLT_23 depends on), and 8084 (the `/.search` example omits resource-level `schemas`). Errata 5050/5295/6010/7122/8097 are interpretation-relevant but match no current test. The two RFCs that update 7644 (RFC 9865 cursor pagination, RFC 9967 async requests) are absent from both the matrix and the suite.

### Cited Findings
Errata list source: [RFC 7644 errata](https://www.rfc-editor.org/errata/rfc7644) (fetched 2026-10-10); page header states "Updated by: RFC9865, RFC9967".

**Verified errata**
- **Erratum 6893 (Verified, Editorial, §7.5.2)**: the non-normative example shows `"status": "404"` under `HTTP/1.1 403 Forbidden`; it should be `"status": "403"`. Impact: any future §7.5.2 test must expect 403 (the normative "SHOULD respond with HTTP status code 403" is unaffected), with `scimType: sensitive` being "may be returned". The current matrix's §7.5.2 Gap row is unaffected, but the example in the RFC must not be copied.
- **Erratum 7916 (Verified, Technical, §3.7.3)**: the bulk failed-operation example is broken JSON (a stray `"status": "201"` line, missing `{`, missing comma). The fix removes the stray line and repairs braces but keeps `"status": "400"` as a **string**. Impact: the suite compares bulk op status as a string (`(op.status as String) == "201"` at [A7:74](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A7_BulkOperationsSpec.groovy#L74) and throughout). The RFC prose, however, says "The status attribute MUST include the code attribute that holds the HTTP response code" while the §3.7.2 response example uses `"status": { "code": "201" }` — an unresolved internal inconsistency. A server implementing the object form would fail BLK_01/02/09/11/12/13/14/15/17. The matrix has no row for this.
- **Erratum 8096 (Verified, Technical, §3.5.2.1)**: missing closing brace in the pathless add example. No test impact (tests build valid payloads).
- **Erratum 8365 (Verified, Technical, §4)**: "defines the endpoints" → "endpoint" (singular). Confirms ResourceType `endpoint` is single-valued; consistent with A1's use of `endsWith` on one endpoint.
- **Erratum 7898 (Verified, Editorial, §3.12)**: the PUT-error example is invalid JSON (missing comma after `"mutability"`); fixed to add a comma. Tests do not consume the literal example.

**Reported errata relevant to interpretation**
- **Erratum 7319 (Reported, §3.4.2.2)**: the published ABNF `*1"not" "(" FILTER ")"` does not permit the space used by the RFC's own example `not (emails co ...)` and by FLT_23 (`not (active eq false)`, [A5_FilteringSpec.groovy:433](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A5_FilteringSpec.groovy#L433)). The proposed fix requires the space (`*1("not" SP)`). Impact: under a strict literal reading of the published ABNF, a server responding 400 `invalidFilter` to FLT_23's filter is defensible, yet the test hard-requires 200 and matching results. Until the erratum is Verified, the expression is ambiguous and the test encodes one side.
- **Erratum 7322 (Reported, §3.4.2.2)** (supersedes Erratum 4690, Held): proposes `valLogExp` recursing into `valFilter` so nested value-path filters like `emails[type eq "work" or (type eq "home" and value ew "@example.com")]` are legal. No current test uses nested value paths; FLT_27 is a simple `valFilter`, so no impact.
- **Erratum 4670 (Held, §3.4.2.2)**: argues the listed precedence (grouping, logical, attribute) is reversed and attribute operators bind tighter. No practical impact on FLT_06/07/23/24, which use explicit parentheses where it matters.
- **Erratum 7122 (Held, §3.5.2)**: `PATH = attrPath / valuePath [subAttr]` should also allow `attrExp`, e.g., `remove` with `path: 'schemas eq "..."'` on a non-complex multi-valued attribute. No current test covers remove-by-value on a scalar multi-valued attribute; PAT_07 uses a complex value path.
- **Erratum 8084 (Held, §3.4.3)**: the `/.search` example response resources omit the required `schemas` member (RFC 7643 §3: "All representations of SCIM schemas MUST include a non-empty array"). Impact: FLT_16/17 assert only the ListResponse schema, so a server that mirrors the RFC's erroneous example response passes; conversely a server that includes resource `schemas` (correct) also passes. No false failure, but the example is not a guide for missing-`schemas` behavior.
- **Erratum 5050 (Reported, §3.7.3)**: the bulk PATCH example's `data` incorrectly contains only the operation list; per §3.7 `data` must be the full body as in a single PATCH, i.e., a PatchOp object with `schemas` + `Operations`. BLK_10 correctly sends the full PatchOp ([A7:474-480](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A7_BulkOperationsSpec.groovy#L474)); the RFC example should not be followed literally.
- **Erratum 5295 (Reported, §3.5.2.1)**: the 204 example includes request headers (`Authorization`) and a `Location`, and the erratum questions whether 204 is valid for the add-already-member case. Impact: all PATCH tests require 200, while RFC §3.5.2 explicitly allows 204; combined with this erratum the 200-only assumption is especially unsafe.
- **Erratum 6010 (Reported, §4 Figure 9)**: the example shows `"itemsPerPage": 10` while the page contains 2 items; the RFC's own example contradicts Table 7 semantics. Supports the audit finding that `itemsPerPage == count` (PAG_01) must not be treated as an RFC requirement.
- **Erratum 8367 (Held, §3.4.1)**: clarifies `{id}` is the value of the `id` attribute. Supports the tests' use of `id` for retrieval; no behavior change.
- **Erratum 8097 (Held, §3.5.2.1)**: documents Microsoft Azure's `add` with a sub-attribute filter path (`emails[type eq "work"].value`) and asks whether it is RFC intent. Current PAT tests do not use add-with-filter; PAT_18's dotted pathless form is a different Entra quirk.

**Normative updates (not errata)**
- **RFC 9865 (Standards Track, Oct 2025) "Cursor-Based Pagination of SCIM Resources"** updates RFCs 7643/7644: defines `cursor` query parameter (URL-safe, opaque), `nextCursor` MUST be present in every paged response except the last page, `previousCursor` optional and MUST NOT appear on the first page, and modifies the `count` description; invoked only when the client uses `cursor` ([RFC 9865 §2](https://www.rfc-editor.org/rfc/rfc9865.txt)). The matrix and suite make no mention.
- **RFC 9967 (Standards Track, May 2026) "SCIM Profile for Security Event Tokens"** updates RFC 7644 with optional asynchronous requests: `Prefer: respond-async` on POST/PUT/PATCH/DELETE → 202, no body, `Set-Txn` header, `Preference-Applied`, `Location`; per-op completion events for bulk ([RFC 9967 §2.5.1](https://www.rfc-editor.org/rfc/rfc9967.txt)). No matrix/suite mention; the coverage matrix should state it audits RFC 7644 as originally published.

### Inferences
- The single most consequential ambiguity for this suite is the bulk `status` representation (prose says object with `code`; examples and the errata fix say string). The suite's string assumption should be documented in the matrix, and the test helper could accept either without weakening anything else.
- 7319 makes FLT_23's `not (` filter legitimate-looking but technically outside the published ABNF; the safest reading is that the example is authoritative intent, but a validator should report—not fail—a 400 here.
- Errata 6893 + the §3.12 Table 9 `sensitive` row mean a future §7.5.2 test should accept 403 (and optionally `scimType: sensitive`), never the example's 404.

### Gaps
- Erratum 7916's fix does not resolve the `status` object-vs-string inconsistency; no erratum addresses it, and RFC 9865/9967 examples use strings. I found no authoritative statement settling it.
- I did not audit RFC 7643 errata (out of scope), which may affect the RFC 7643-adjacent claims used by these tests (e.g., `meta.version`/ETag semantics, Group `displayName` required/uniqueness).
- Datatracker's HTML views of drafts that became RFC 9865/9967 were not compared against the published text; findings use the published RFCs.
