# SCIM 2.0 Industry Conformance Practice: Validators, Common Gaps, Client Behavior, Standards Context (through 2026)

Scope note: This research feeds an assessment of how complete/trustworthy the scim-validator suite's RFC 7643/7644 coverage is (repo default target: api.scim.dev; explicit interop tests for Microsoft Entra ID PATCH dialects). Emphasis on 2025–2026 sources; vendor documentation is distinguished from opinion/engineering blogs.

---

## Q1. Which open-source and commercial SCIM test/conformance suites exist, and which RFC sections do they cover or skip?

### Takeaway
There is no formal certification program for SCIM 2.0. The landscape consists of a handful of small open-source test runners plus vendor-hosted compatibility validators, each of which tests a pragmatic subset (discovery, User/Group CRUD, filter/pagination/PATCH, sometimes bulk/sort/ETag) and explicitly disclaims completeness. No public source found claiming full RFC 7643/7644 coverage with published coverage metrics.

### Cited Findings
- **SCIM Verify (limosa-io/scimverify)**: open-source (GPLv3) conformance runner, runnable via `npx scimverify --base-url ... --auth-header ...`; online at scim.dev/verify (verify.scim.dev now redirects there). Its own "About" page states it "inspect[s] discovery endpoints, validate[s] common response shapes, and exercise[s] Users and Groups flows such as list, retrieve, filter, sort, paginate, create, replace, patch, and delete" and explicitly says "It is a practical interoperability check, not a formal certification program. Passing the tests is a useful signal, but it does not prove complete compliance or production readiness." Free tier is limited to GET checks on /Users; Pro (€9.99/mo) unlocks create/replace/patch/delete provisioning checks. Repo README's feature list is only "Validate SCIM endpoints / Check compliance / Generate detailed reports" — no published per-RFC-section coverage table. — [scim.dev/verify/about](https://scim.dev/verify/about); [GitHub limosa-io/scimverify](https://github.com/limosa-io/scimverify); [verify.scim.dev redirect notice](https://verify.scim.dev/)
- **WSO2 SCIM 2.0 Compliance Test Suite (incubator)**: GSoC 2017 project; takes a SCIM base URL, drives a proxy, and produces a PDF report "indicating the coverage percentage of each specification" plus per-test request/expected/actual. README test inventory: /Users (create, get, delete, list, pagination, PUT, sorting, filtering, PATCH), /Groups (same), /Me (create, get, delete, PUT, PATCH), EnterpriseUser (same as Users), /ServiceProviderConfig (get), /ResourceType (get), /Schemas (get), /Bulk (create). This is the only tool found that advertises spec-coverage percentages. — [GitHub wso2-incubator/scim2-compliance-test-suite](https://github.com/wso2-incubator/scim2-compliance-test-suite)
- **suvera/scim2-compliance-test-utility**: Java/Spring Boot web UI (Docker image `suvera/scim2-compliance-test-utility:1.0.3`, ~22 GitHub stars, MIT); README describes it as a "compliance test utility" but publishes no test inventory or coverage details beyond screenshots and links to the suvera scim2-sdk. — [GitHub suvera/scim2-compliance-test-utility](https://github.com/suvera/scim2-compliance-test-utility)
- **scim-sanity (thomaselliottbetz)**: small Python MIT project (3 GitHub stars as listed) that probes a live server ("prioritized list of RFC 7643/7644 violations with fix guidance") and lints payloads; has a "server profile" concept (starting with Microsoft Entra ID) to inject non-RFC fields real servers require; probe is destructive and requires `--i-accept-side-effects`; validates Discovery, User/Group/Agent lifecycle, Search, Error Handling. No formal coverage metric. — [PyPI scim-sanity](https://pypi.org/project/scim-sanity/); [GitHub scim-sanity](https://github.com/thomaselliottbetz/scim-sanity)
- **Microsoft Entra ID SCIM Validator** (commercial, free web tool): scimvalidator.microsoft.com tests a server against what the Entra ID SCIM *client* needs; onboarding offers default attributes, schema discovery via the server's /Schemas endpoint, or uploaded Entra app schema. The Entra tutorial enumerates exactly what the validator checks: create user (+ duplicate-user 409 check), get user, get-by-filter, update multi-valued/single-valued attributes incl. joining property change, disable via active=false, delete, create group (+ duplicate 409), get group with `excludedAttributes=members`, get by displayName, update group non-member attrs, add/remove members via PATCH. — [scimvalidator.microsoft.com](https://scimvalidator.microsoft.com/); [Microsoft Learn: use SCIM to provision users and groups](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- **Microsoft Azure AD SCIM reference code + sample endpoint**: open-source .NET endpoint (Microsoft.SCIM library) advertised as a way to "test it out by running through the sample requests/responses" — a reference implementation, not a conformance runner. — [Microsoft Learn (same tutorial)](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- **Okta SCIM spec test suite (Runscope/BlazeMeter)**: Okta publishes a JSON test file `Okta-SCIM-20-SPEC-Test.json` (plus 1.1 equivalent) to import into Runscope API monitoring, with an initial-script that generates random users including "randomUsernameCaps … to test case sensitivity" and a nonexistent UserId; test success is judged by HTTP status of GET/POST requests. Okta notes OIN submissions must adhere to SCIM 2.0. — [Okta: Build your SCIM API service](https://developer.okta.com/docs/guides/scim-provisioning-integration-prepare/main/); [Okta-SCIM-20-SPEC-Test.json](https://developer.okta.com/standards/SCIM/SCIMFiles/Okta-SCIM-20-SPEC-Test.json)
- **Ping Identity / UnboundID SCIM 2.0 SDK for Java** (Apache-2.0; "The UnboundID SCIM 2.0 SDK for Java", copyright through 2026; client docs at version 6.0.0 published 2026-05-11): ships an in-repo server test framework (`scim2-sdk-server/.../EndpointTestCase.java`, ~1500 lines) covering ServiceProviderConfig retrieval, schemas/resource-types retrieval, /Me with attributes query params, create, bulk response deserialization, 404 handling — i.e., SDK-level endpoint tests, not a standalone conformance report tool. A web search found no evidence of a public, standalone Ping/UnboundID "SCIM 2.0 test tool" beyond this SDK; Ping's product docs list a PingDirectory SCIM 2.0 API reference and a PingOne for Enterprise Directory API based on SCIM. — [pingidentity/scim2 repo](https://github.com/pingidentity/scim2); [EndpointTestCase.java](https://github.com/pingidentity/scim2/blob/master/scim2-sdk-server/src/test/java/com/unboundid/scim2/server/EndpointTestCase.java); [javadoc 6.0.0](https://javadoc.io/static/com.unboundid.product.scim2/scim2-sdk-client/6.0.0/index.html); [Ping APIs page](https://developer.pingidentity.com/apis.html)
- **api-scenario SCIM scenario (Thomas Poignant blog, 2020)**: an older CLI-driven scenario file asserting required API responses; posted as a community gist, not maintained as a product. — [Medium: Test your SCIM implementation](https://thomaspoignant.medium.com/test-your-scim-implementation-70d050f42110)
- **Community registries/hubs**: [scim.cloud](https://scim.cloud) is the community hub (also listed by the IETF SCIM WG as its website) with a JSON implementations registry at [aaronpk/scim.cloud](https://github.com/aaronpk/scim.cloud/blob/main/public/json/scim_v2_implementations.json). The registry lists both client and server implementations (e.g., Okta as client, ServiceNow as both) but has no conformance claims.
- **Repo-internal context (for the report)**: a modernizer-style tool also exists: [askmeidentity SCIM payload validator](https://askmeidentity.com/tools/scim-payload-validator) validates a single User/Group payload against "RFC 7643 + RFC 7644 schemas" (static validation only).

### Inferences
- Tools cluster into two kinds: (1) generic spec runners that mutate resources and check protocol behavior (WSO2, SCIM Verify, suvera, scim-sanity), overlapping the scim-validator suite; (2) vendor compatibility validators (Microsoft, Okta/Runscope) that encode one client's dialect rather than the RFC. The scim-validator suite's planned Entra PATCH dialect tests parallel category (2) but are usually only offered by the vendor.
- None of these tools publish audited coverage matrices tied to RFC section numbers except WSO2 (percentage claim, unverified externally), so "coverage completeness" claims are generally self-attested.
- Only Microsoft's validator documents a two-client check (duplicate creation → 409) and case-sensitivity checks (Okta), which are exactly the failure modes found in the gap literature (see Q2).

### Gaps
- No reliable public evidence found of a commercial SCIM *certification* program (e.g., "SCIM Certified") from any standards body or vendor; SCIM Verify explicitly disclaims being one.
- Could not verify WSO2's coverage-percentage claims against its (GSoC-era) code; repo status/applicability in 2026 not confirmed.
- suvera and scim-sanity lack documented test inventories; their actual RFC-section coverage could not be confirmed from READMEs.
- No public inventory found for Ping Identity's internal conformance testing; only the SDK's own endpoint test file was found.
- No SSR/CSV export of coverage from any tool was found except WSO2's PDF report claim.

## Q2. Documented common server non-conformances for RFC 7643/7644 (filters, PATCH, bulk, ETag, content negotiation, returned/password, userName comparison, pagination, /.search)

### Takeaway
The most frequently documented server failures are: missing discovery endpoints, wrong PATCH semantics (path/op handling, multi-valued filters, non-boolean values), malformed SCIM error bodies, wrong `totalResults`/metadata, case-mangling of stored values, and missing `application/scim+json`. Filter support beyond `eq`/`and` is rare in practice; bulk, sort, ETag and `.search` are commonly absent and increasingly deprioritized by the ecosystem.

### Cited Findings
- **Traxion: "10 most common pitfalls" (vendor consultancy blog, 2020, author tested 40–50 SCIM APIs)** — the single most concrete field list found:
  1. Testing with generic API IDE instead of SCIM-aware tools; 2. altering the core schema (missing/renamed attrs, changed types/mutability); 3. extending the core schema without schema extensions; 4. confusing `id` vs `externalId`; 5. malformed error responses (must follow RFC 7644 §3.7.3); 6. missing/incorrect metadata — e.g., filtered GET returning `totalResults` = page size instead of the total matching count; 7. missing mandatory configuration endpoints (/ServiceProviderConfig, /ResourceTypes, /Schemas) — noting "most of these already implemented SCIM APIs are developed for Azure AD integration" and that Entra's client does not require the mandatory discovery endpoints; 8. PATCH quality "differs from bad to mediocre" and PATCH is optional while PUT is required; 9. not preserving input casing of string values (causes cross-system update loops); 10. over-complex authorization models lacking an RBAC group model. — [Traxion blog](https://www.traxion.com/blog/the-10-most-common-pitfalls-for-scim-2-0-compliant-api-implementations)
- **Microsoft Entra known-compliance-issues doc (vendor, dated 2025-08-25)**: acknowledges Entra's own client non-conformances over time: requires "/scim" in root URL — fixed 2018-12-18; extension attributes used dot instead of colon notation — fixed 2018; PATCH multi-value path filter syntax invalid — fixed 2018; group-creation invalid schema URI — fixed 2018; "Update PATCH behavior to ensure compliance (such as active as boolean and proper group membership removals)" — **NOT fixed**, status "No / TBD", still behind feature flag `aadOptscim062020`. Non-flagged behavior includes `op` values `Add/Replace/Remove` (capitalized), `"value": "False"` (string) for `active`, path-less multi-attribute Replace, and Remove-members without a filter on `members`. — [Microsoft Learn: Known issues with SCIM 2.0 protocol compliance](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/application-provisioning-config-problem-scim-compatibility)
- **Microsoft Entra build-a-SCIM-endpoint requirements (vendor)**: client "only uses the following operators: `eq`, `and`"; queries must be filterable on the configured matching attribute (e.g., `userName eq`, `emails[type eq "work"].value eq`); responses to queries must always be a ListResponse; all responses should have `Content-Type: application/scim+json`; don't send null values; property values camelCase (e.g., `readWrite`); `type` sub-attribute values of multi-valued attributes must be unique; group `displayName` must be unique (beyond RFC); do not case-fold PATCH `op`; store values as sent (no phone-number reformatting); `id` required on every returned resource; soft-delete via `active=false` and restored users must still be returned by GET; `/Schemas` required for gallery/schema discovery; Groups require PATCH support; `excludedAttributes=members` must be supported when querying groups. — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- **Interop-profile draft (draft-zollner-scim-interop-profile-01, individual I-D, Okta author, April 2026)** defines the restricted subset that the ecosystem considers necessary and lists the variations "that have proven to be common sources of interoperability failure": PATCH syntax, pagination, filtering, case sensitivity, error handling. Its rules: clients MUST use only `eq` and `and`; filters in URIs of non-GET methods (e.g., `PATCH /Users?filter=`) MUST NOT be used; every PATCH operation MUST have a `path` (path-less is rejected 400 `invalidSyntax`); path filters must target a sub-attribute (e.g., `emails[type eq "work"].value`), targeting the element itself is prohibited; `count` default SHOULD be ≥100 and at least 100 MUST be supported; unknown schema/attributes MUST be rejected 400 `invalidSyntax`; uniqueness conflicts MUST be 409 `uniqueness`; **clients MUST NOT send `If-Match`/ETag headers and servers MAY ignore or reject them**; DELETE must actually delete (not merely set `active=false`); `/Bulk` is OPTIONAL. — [draft-zollner-scim-interop-profile-01](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/)
- **WorkOS engineering blog (vendor, 2025-11-10)**: "PATCH semantics: Some providers deviate from the standard, requiring workarounds for multi-valued attributes. Filtering and pagination: Implementations of filter parameters and startIndex handling vary widely. Bulk operations: Many IdPs claim to support them, but their behavior under load can differ." Also notes Entra ID supports only a subset of SCIM filter syntax and Okta "often sends unexpected PATCH payloads." — [WorkOS: Why building SCIM is hard](https://workos.com/blog/why-building-scim-is-hard)
- **WorkOS SCIM best practices (vendor, 2025-05-26)**: schema-handling fragmentation example — Entra "requires adding the proper schema extension as a prefix … and the attributes will always come in nested," while Okta shows core-prefixed attributes top-level; custom extension attributes are a common divergence point; `externalId` semantics differ (Okta keeps user data for audit; some providers purge); concurrent/out-of-order requests require idempotent/race-safe handling. — [WorkOS: SCIM best practices](https://workos.com/guide/scim-best-practices)
- **Real-world partial implementations (evidence that optional features are routinely skipped)**: Posit Connect SCIM API reference explicitly lists "Bulk operations — Not supported; Current user (/Me) — Not supported; Change password — Not supported; Sorting — Not supported; ETags — Not supported; Filter operators other than eq — Not supported"; and DELETE "returns 204 but does not delete." — [Posit Connect SCIM API reference](https://docs.posit.co/connect/admin/appendix/scim/api-reference.html)
- **GitLab SCIM API (real implementation)**: documents that it supports only simple filter expressions (SSO-linked GitLab SCIM v2 endpoints; users looked up via `extern_uid` filter) and PATCH with simple paths like `name.formatted`; it is documented as internal-use/changeable, illustrating that SCIM endpoints are often narrow subsets. — [GitLab SCIM API docs](https://doc-zip-test.staging.gitlab.io/ee/api/scim.html) (observed mirror; canonical docs live at docs.gitlab.com/ee/api/scim.html)
- **scim.dev implementation checklist (vendor-adjacent)**: recommends implementing "common filters such as `userName eq "..."` and `externalId eq "..."`"; stable `startIndex`, `itemsPerPage`, `totalResults`, `Resources`; empty-result and paginated-list testing; retry/idempotency for group membership changes; not logging bearer tokens. — [scim.dev checklist](https://scim.dev/guide/scim-implementation-checklist.html)
- **Microsoft Entra gallery onboarding requirements (vendor)**: server "Required: Support schema discovery", "Recommended: Support updating multiple group memberships with a single PATCH request", "Recommended: Support SCIM bulk APIs to improve connector performance"; Entra's own docs say "While we don't support SCIM /Bulk today, this is something we aim to support in the future" (client-side). Also requires OAuth 2.0 client credentials or workload identity federation — Basic auth and long-lived bearer tokens rejected for gallery onboarding (Chapter 3 client behavior). — [Microsoft Learn: Gallery app provisioning requirements](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/app-gallery-user-provisioning-requirements)
- **OneLogin (vendor)**: required API calls from its SCIM client are: Get User with `userName` filter, Create User, Get User by ID, Update User, Get Groups, Create Group, Patch Group, Delete User, Get Users; initial connection is a filter lookup for a nonexistent userName where empty list or 404 confirms the endpoint; Patch Group expects 204. — [OneLogin: Implement RESTful SCIM APIs](https://developers.onelogin.com/scim/implement-scim-api)
- **Case sensitivity**: Traxion pitfall 9 (store/return same casing); Okta's test suite generates an uppercase-username variable specifically "to test case sensitivity" and expects an invalid-user 404 flow. The interop profile requires `userName` treated case-insensitively for both filtering and uniqueness, and `id`/`externalId` case-exact. — [Traxion](https://www.traxion.com/blog/the-10-most-common-pitfalls-for-scim-2-0-compliant-api-implementations); [Okta prepare guide](https://developer.okta.com/docs/guides/scim-provisioning-integration-prepare/main/); [interop profile](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/)
- **Content negotiation / media type**: RFC 7644 registers `application/scim+json` (IANA media type; "Older versions of SCIM are known to informally use application/json") — the interop profile makes `application/scim+json` mandatory on all requests/responses. — [RFC 7644](https://datatracker.ietf.org/doc/rfc7644); [interop profile](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/)
- **Uniqueness/409 behavior**: interop profile requires HTTP 409 + `scimType: uniqueness` for duplicate userName/emails; Google Cloud IAM SCIM (Workforce Identity Federation) documents that duplicate mapped `google.subject`/`google.group` values fail with HTTP 409 and null/empty mapped attributes with HTTP 400. — [interop profile](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/); [Google Cloud IAM SCIM provisioning](https://docs.cloud.google.com/iam/docs/workforce-identity-federation-scim)
- **Security-oriented findings (Doyensec, security consultancy blog, May 2025)** — concrete implementation bug classes found in real SCIM servers: unauthenticated SCIM endpoints enabling auth bypass/admin creation (example: Casdoor, fixed in v1.812.0), SCIM token management flaws, unwanted user re-provisioning fallbacks, internal attribute manipulation via SCIM payloads, verification bypasses, account takeover; notes "SCIM does not define its authn/authz method, hence it will always be custom" and multi-tenant isolation is a recurring defect class. — [Doyensec: SCIM Hunting — Beyond SSO](https://blog.doyensec.com/2025/05/08/scim-hunting.html)
- **Rate limiting / 429 (Okta client behavior, vendor)**: Okta pauses and retries on HTTP 429; honors integer-seconds `Retry-After`, otherwise defaults to 5 minutes; exponential backoff up to 10 attempts; non-integer/HTTP-date Retry-After is ignored (defaults 5 min). Servers therefore effectively need 429 + Retry-After (seconds) to behave well with Okta. — [Okta: Understanding SCIM](https://developer.okta.com/docs/concepts/scim/)

### Inferences
- The features the scim-validator suite emphasizes beyond `eq` filtering (gt/ge/lt/le, value paths), bulk, ETag, sorting, `/Me`, `/.search` are precisely the ones the dominant clients do not exercise, and some (ETag/If-Match) are actively deprecated by the emerging interop profile. This means the suite likely over-tests relative to real-world client demand — valuable for spec completeness, but results should be weighted accordingly in any "trustworthiness" assessment.
- Conversely, suite coverage of Entra's non-conformant PATCH dialect is justified: Microsoft still ships non-compliant PATCH by default in 2026 (feature flag, "TBD"), so real interop requires tolerating both RFC and Entra dialects.
- `totalResults` correctness on filtered queries, error-body shape (`scimType`), casing preservation, discovery endpoints, and 409 duplication are the highest-frequency documented server defects; any suite should treat them as first-class.
- No source found documents a `/Bulk` 413 payload-limit behavior or tests for it; bulk limits appear untested by every tool reviewed.

### Gaps
- **PRECIS userName comparison**: no source found discussing PRECIS (RFC 8264/8265) for SCIM `userName`; RFC 7643 defines `userName` as caseExact=false and vendors document case-insensitivity, but no 2025–2026 work or advisory found on Unicode/PRECIS-level comparison. Treated as an unanswered question.
- **returned=never / password leakage**: only indirect evidence found (Entra schema table shows `ownedGroups` with `returned: never`; Entra doc says `password` is required for managed-domain users) — no specific security advisory or conformance test found targeting `returned=never` violations or password attribute leakage. [Microsoft schema documentation](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/entra-id-scim-api-schema-documentation)
- **Bulk 413 limits**: no vendor or tool documentation found describing payload-size limits or 413 testing.
- **/.search and /Me**: no vendor documentation found that Entra, Okta, OneLogin or Google exercise `/.search` or `/Me`; only test tools (WSO2, scim.dev playground) cover them.
- gt/ge/lt/le operator support is rarely documented by clients; only the interop profile's negative requirement (clients MUST NOT use operators other than eq/and) speaks to it.

## Q3. What capabilities do Entra ID and Okta effectively require, and which optional RFC features do they not use?

### Takeaway
Both clients effectively require a small core: CRUD on Users, filter-by-join-attribute, PATCH for updates, stable server-issued `id`, `active` soft-delete semantics, discovery (/Schemas at minimum; /ServiceProviderConfig and /ResourceTypes for correct tooling), and scim+json content type. Neither uses bulk for provisioning, sorting, ETags/If-Match, `/Me` or `/.search`; filter syntax in practice is `eq`/`and` only. OneLogin adds group operations and userName-filter lookup; Google historically used its own API and in 2026 GA'd inbound SCIM with Google as *server*.

### Cited Findings (Entra ID)
- Required by Entra: create users (optionally groups) RFC 7644 §3.3; modify via PATCH §3.5.2; retrieve known resource §3.4.1; query users/groups §3.4.2 (by `id`, and by `userName`/`externalId` for users, `displayName` for groups); `excludedAttributes=members` on group GET §3.4.2.2; list+pagination §3.4.2.4; soft delete/restore via `active`; `/Schemas` endpoint; single bearer token auth. — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
- Entra's client uses only the `eq` and `and` filter operators; any attribute used for uniqueness must be filterable; queries that fail should return ListResponse (200 with zero resources is documented). — same URL.
- Entra "makes requests to fetch a random user and group to ensure that the endpoint and the credentials are valid" (Test Connection), and group provisioning requires PATCH support; group `displayName` uniqueness is an Entra requirement beyond the RFC. — same URL.
- Entra historically required "/scim" in the endpoint path; now configurable but the doc still notes the old behavior/flag. PATCH compliance remains behind `aadOptscim062020`; downgrade flag `AzureAdScimPatch2017`. — [Microsoft Learn: Known SCIM 2.0 compliance issues](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/application-provisioning-config-problem-scim-compatibility)
- Gallery requirements (for app vendors seeking listing): SCIM 2.0 user+group endpoints (users required, groups recommended); **at least 25 requests/second per tenant**; schema discovery required; multi-membership single PATCH recommended; bulk APIs recommended for connector performance; OAuth 2.0 client credentials or workload identity federation (RFC 7523 JWT bearer) — Basic auth and long-lived bearer tokens not accepted for gallery onboarding; client secret 1–3 year lifetime; engineering/support contacts and published SCIM docs required; ≥100 mutual customers via non-gallery before listing. — [Microsoft Learn: App gallery user provisioning requirements](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/app-gallery-user-provisioning-requirements)
- Entra ID's *own* SCIM server API (inbound provisioning into Entra) states it is based on RFC 7642/7643/7644 **and RFC 9865 (cursor-based pagination)**; publishes `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`, `/Users` (GET, POST, PATCH, DELETE) with `attributes`/`excludedAttributes` query params; requires enabling an access-token flow. — [Microsoft Learn: Microsoft Entra ID SCIM API reference](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/entra-id-scim-api-reference)
- TLS: Entra requires TLS 1.2 only for SCIM endpoints, RSA ≥2048 / ECC ≥256, specific ECDHE cipher suite list; IP ranges for the provisioning service documented. — [Microsoft Learn: Develop a SCIM endpoint](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)

### Cited Findings (Okta)
- Minimum required feature set for Okta SCIM 2.0 (OIN submissions must be 2.0; Okta also supports 1.1 for private integrations): endpoints structured per RFC 7644 §3.2; HTTPS; authentication via OAuth 2.0 authorization code, Basic, or HTTP Authorization header (refresh token support optional); base URL without underscore, recommended `/scim/v2/`; must store `userName`, `name.givenName`, `name.familyName`, `emails`; server-assigned stable `id` (case-sensitive, read-only, never empty, immutable, unique; "You can't use the string `bulkId` within any unique identifier value"); `active` boolean required. — [Okta: Build your SCIM API service](https://developer.okta.com/docs/guides/scim-provisioning-integration-prepare/main/)
- Okta's official test flow is the Runscope/BlazeMeter spec-test JSON; the initial script defines `InvalidUserEmail`, random usernames incl. `randomUsernameCaps` (case-sensitivity test), `UserIdThatDoesNotExist`; the test then creates users and checks responses; results can be shared with Okta for OIN submission. — same URL.
- Okta deprovision semantics: deactivating in Okta sets `active=false` via PATCH; deleting an already-deactivated Okta profile does NOT send DELETE to the SCIM app; importing from app to Okta is a separate flow ("profile sourcing"); Okta does not pull in users with `active=false` even on full import. — [Okta: Understanding SCIM](https://developer.okta.com/docs/concepts/scim/)
- Okta 429 handling: pauses task, honors integer-seconds `Retry-After` (else 5-min default), exponential backoff, max 10 attempts then permanent failure. — same URL.
- Okta keeps SCIM 1.1 support, and states "OIN integration submissions must adhere to the SCIM 2.0 specification." — [Okta prepare guide](https://developer.okta.com/docs/guides/scim-provisioning-integration-prepare/main/)

### Cited Findings (OneLogin)
- Supports SCIM 1.1 and 2.0. Required calls: Get User with userName filter, Create User, Get User by ID, Update User, Get Groups, Create Group, Patch Group, Delete User, Get Users; initial connectivity check is `Get User by userName` for a nonexistent value, expecting empty array or 404; Patch Group expects 204; UI integration uses a "SCIM Provisioner with SAML (SCIM v2 Core)" app with SCIM Base URL + Bearer Token. — [OneLogin: Implement SCIM APIs](https://developers.onelogin.com/scim/implement-scim-api); [Kisi docs example](https://docs.kisi.io/marketplace/identity_management/scim/onelogin)

### Cited Findings (Google)
- Historically (2016) Google Workspace added outbound automated provisioning "using SCIM 2.0" as a *client* to apps like Salesforce, with deprovisioning delay configuration. — [Google Workspace Updates, 2016](https://workspaceupdates.googleblog.com/2016/07/automatically-provision-users-with-scim.html)

A server can pass both vendors' validators while failing much of RFC 7644 (bulk, sort, ETags, rich filters, /Me, /.search, PUT semantics).

## Q5. Standards context through 2026: errata, IETF SCIM WG status, successor work, ISO, security advisories

### Takeaway
SCIM standards work is alive and accelerating in the IETF: the SCIM WG is Active and chartered to revise RFC 7642/7643/7644 toward Internet Standard; RFC 9865 (cursor pagination, Oct 2025) and RFC 9967 (SCIM Security Event Tokens profile, May 2026) both update 7643/7644. No ISO/IEC standardization of SCIM was found. Security literature focuses on bespoke auth/authz and token handling rather than protocol CVEs; no SCIM-specific IETF security advisory was found.

### Cited Findings
- **IETF SCIM WG status (fetched 2026)**: Active WG in the Security Area; chairs Aaron Parecki and Nancy Cam-Winget; AD Christopher Inacio; mailing list scim@ietf.org; chat on Zulip; website scim.cloud; GitHub org ietf-scim-wg. Charter goals: revise RFC 7642 (use cases: pull/push, events/signals, deletion), revise RFC 7643/7644 for Internet Standard maturity (including profiling SCIM relationships with OAuth 2.0, OIDC, Shared Signals, FastFed; `externalId` evolution; account-state context), multi-value query filtering and paging (input: draft-hunt-scim-mv-paging), domain coordination/synchronization (RFC 8417/draft-hunt-idevent-scim), soft deletes (draft-ansari-scim-soft-delete), credential discovery/attribute mapping/per-attribute schema negotiation, HR/enterprise-group/PAM extensions (draft-grizzle-scim-pam-ext). Milestones date from 2021–2023 (atom feed shows active work continuing). — [IETF Datatracker: scim WG](https://datatracker.ietf.org/wg/scim/about/)
- **RFC 9865 — Cursor-Based Pagination of SCIM Resources (Proposed Standard, October 2025)**: updates RFCs 7643/7644; defines `cursor` query param and `nextCursor` response attribute, optional `pagination` sub-attributes (`cursor`, `index`) in ServiceProviderConfig; servers supporting cursor pagination MUST include `nextCursor` in all paged responses except the last; new implementations SHOULD default to index pagination when no params given. Produced by the IETF SCIM WG (was draft-ietf-scim-cursor-pagination; shepherd write-up; IESG approved). Authors: M. Peterson (Entrust), D. Zollner, A. Sehgal (AWS). — [RFC 9865](https://www.rfc-editor.org/rfc/rfc9865.html); [Datatracker](https://datatracker.ietf.org/doc/rfc9865)
- **RFC 9967 — SCIM Profile for Security Event Tokens (SETs) (Proposed Standard, May 2026)**: updates RFC 7643/7644; defines SCIM events via RFC 8417 SETs (`urn:ietf:params:scim:event:feed:*`, `prov:create|patch|put|delete|activate|deactivate`, `misc:asyncresp`), asynchronous requests via `Prefer: respond-async` and a new `Set-Txn` HTTP response header, plus `securityEvents` discovery attributes in ServiceProviderConfig. Authored by P. Hunt (Independent Id), N. Cam-Winget (Cisco), M. Kiser (SailPoint), J. Schreiber (Workday); from draft-ietf-scim-events. — [Datatracker RFC 9967](https://datatracker.ietf.org/doc/rfc9967/)
- **Errata**: RFC 7643 has verified Technical erratum EID 8415 (reported 2025-05-14, verified 2025-10-28): in the Schema Definition (§8.7.1) `binary` is missing from the allowed attribute types/canonicalValues, and `complex` must not be listed as a valid sub-attribute data type (complex attributes cannot contain complex sub-attributes, §2.3.8); it references erratum 5606 applying the same binary fix. Both RFC 7643 and 7644 are marked "Updated by RFC 9865, RFC 9967" on Datatracker / RFC Editor. — [RFC Errata EID 8415](https://errata.rfc-editor.org/eid8415); [Datatracker RFC 7643](https://datatracker.ietf.org/doc/rfc7643); [Datatracker RFC 7644](https://datatracker.ietf.org/doc/rfc7644)
- **Interop-profile draft (individual, not IETF-endorsed)**: draft-zollner-scim-interop-profile-01 (Danny Zollner, Okta; last updated 2026-04-15; expires 2026-10-17) — explicitly "not endorsed by the IETF and has no formal standing"; restricts SCIM to a common subset (eq/and only, mandatory PATCH path, no PUT for updates, no ETags/If-Match, bulk optional, TLS 1.3 required/TLS 1.2 allowed, Basic auth NOT RECOMMENDED, `interopProfileConformant` flag in ServiceProviderConfig). — [draft-zollner-scim-interop-profile-01](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/)
- **ISO/IEC**: searches for SCIM ISO/IEC standardization returned only unrelated ISO standards; **no evidence found that SCIM 2.0 has been adopted as an ISO/IEC standard** as of 2026. The standards track for SCIM is the IETF (Internet Standard maturity per WG charter), not ISO. (Negative finding — see Gaps.)
- **Security advisories / breaches**: no SCIM-specific IETF security advisory or CVE affecting RFC 7643/7644 was found. The most substantive 2025 public security write-up is Doyensec's "SCIM Hunting — Beyond SSO" (May 2025) cataloguing real implementation vulnerabilities (unauthenticated SCIM endpoints e.g. Casdoor fixed in v1.812.0, token management, re-provisioning fallbacks, internal attribute manipulation, account takeover) and noting SCIM defines no authn/authz mechanism itself. RFC 7644's own security considerations (bearer token entropy per RFC 6750/6819, TLS mandatory) remain the normative guidance; Microsoft's endpoint requirements add TLS 1.2 + cipher constraints; Okta's 429/Retry-After behavior is the main operational security/robustness contract surfaced. — [Doyensec](https://blog.doyensec.com/2025/05/08/scim-hunting.html); [RFC 7644](https://datatracker.ietf.org/doc/rfc7644); [Microsoft Learn TLS requirements](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)

### Inferences
- As of 2026, RFC 7643/7644 are still Proposed Standards from 2015, amended incrementally (9865, 9967) while a full revision to Internet Standard is in the WG pipeline. A validator suite claiming RFC 7643/7644 coverage should clarify whether it targets the 2015 text, the current RFC 9865/9967 amendments, or the future revision — client behavior (e.g., Entra's RFC 9865 mention, interop profile's RFC 9865 dependency) is beginning to follow the amendments.
- ETag/If-Match testing in the suite tests behavior that the interop profile actively tells clients not to use; cursor pagination (RFC 9865) is the newer stuff worth watching but adoption evidence is thin (only Microsoft's inbound Entra SCIM API reference explicitly cites it among fetched sources).
- The absence of protocol-level CVEs suggests SCIM conformance tooling has more value for interoperability than for security assurance; security findings live in implementations, not the RFC.

### Gaps
- No evidence of ISO/IEC adoption of SCIM; if any national/regional standardization exists, it was not found. Report should state this as a negative finding, not as proof of nonexistence.
- Exact current status/name of any WG revision draft of 7643/7644 (e.g., a `draft-ietf-scim-*` published revision) was not located in the time available; the charter and milestones confirm intent and active state, but the revision documents' latest versions were not enumerated.
- No SCIM-specific OWASP guidance page or security advisory was found; OWASP material is generic on bearer tokens/OAuth. The suggested "OWASP guidance on SCIM" may not exist as a distinct artifact.
- No public breach write-up explicitly attributed to SCIM protocol misuse (as opposed to implementation bugs) was found.

## Meta-observations for the scim-validator coverage report (cross-question inferences)

- The industry has **no authoritative "SCIM conformance" bar**: every tool self-describes as a practical check. Any statement that the suite's coverage is "complete" or "trustworthy" must be relative to a chosen baseline — e.g., RFC section inventory vs. Entra/Okta/Runscope-check-for-check vs. the new interop profile restriction.
- The most defensible external benchmarks to compare the suite against: (1) Microsoft's documented validator checks (incl. duplicate-409, active=false, excludedAttributes=members, group member add/remove PATCH); (2) Okta's Runscope spec test (case sensitivity, invalid ID); (3) WSO2's inventory (includes /Me, /Bulk, sorting, EnterpriseUser); (4) the interop-profile restriction list (what the ecosystem says actually breaks interop); (5) RFC 9865 cursor pagination as the newest normative surface.
- api.scim.dev being both the default target and operated by the same org that publishes a verifier means the suite can be exercised exhaustively there, but "passes against api.scim.dev" says nothing about third-party conformance norms.
- Where the suite tests features (bulk, ETag, sort, /Me, gt/ge/lt/le, .search), documented real-world demand is low and sometimes negative; where the suite should be strongest for credibility is error semantics (`scimType`, 409 uniqueness), totalResults/pagination correctness, PATCH path/dialect breadth (RFC + Entra), discovery endpoints, and scim+json handling — the exact areas the literature identifies as common failures.
