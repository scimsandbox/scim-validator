# SCIM coverage matrix overstates what tests prove

The scim-validator suite's **186 tests** genuinely exercise a broad, high-value slice of RFC 7643 and RFC 7644 — User/Group CRUD, PATCH, filtering, pagination, sorting, bulk, discovery, ETags — but a line-by-line audit of the RFC texts against the actual assertions shows the coverage artifacts overstate what those tests prove. The 119-row matrix ([SCIM_SPEC_COVERAGE.md](file:///Users/eduardpal/work/scim2/scim-validator/SCIM_SPEC_COVERAGE.md)) counts 48 Covered / 43 Partial / 28 Gap, yet it contains seven material RFC 7644 errors — including a swapped §3.5.2.2/§3.5.2.3, a wrong RFC section number for create, and a `Content-Location` requirement attributed to the wrong RFC — plus four misleading RFC 7643 citations, and **at least 15 normative RFC 7644 requirements and roughly 20 RFC 7643 requirements have no matrix row at all**. The companion tracker ([SCIM_VALIDATOR_ASSESSMENT.md](file:///Users/eduardpal/work/scim2/scim-validator/SCIM_VALIDATOR_ASSESSMENT.md)) is worse: its "99% complete, all gaps CLOSED" claim is contradicted by code in which **21 `scimType` call sites pass when the keyword is omitted**, optional features (PATCH, bulk, ETag, `/.search`, Enterprise extension) are hard-required despite being optional in the RFC, and several deviation-tolerance branches can never fail a run. The practical consequence is that **a green run proves interoperability on the paths the suite exercises, not conformance** to RFC 7643/7644; and because the audit was static — the suite was never executed — every statement here is a code/claim analysis, not an observed pass/fail. The fix is well-scoped: strict-mode `scimType`, capability gating, and machine-readable deviations would make the Covered/Partial/Gap labels defensible.

## The protocol core is covered, but its edges are soft or unstated

The audit resolved every `Test(s)` reference in the RFC 7644 half of the matrix against the `def` line in the named spec file and checked each status against the actual assertions ([RFC 7644 coverage audit](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/01_rfc7644_protocol_coverage.md)). Most line references are accurate, and the sustained coverage is real: authentication failures return 401 with `WWW-Authenticate` (SEC_01/02/15), create asserts 201 plus `Location` plus `meta.resourceType` (USR_01/GRP_01/BLK_01), GET-by-id and 404-on-every-verb are strict including SCIM Error bodies (USR_03/04, GRP_02/09, NEG_03–06), PATCH atomicity is tested with a real rollback scenario (PAT_15/16), bulk `bulkId` cross-references are exercised both in `data` and in paths (BLK_07/08), and ETag concurrency covers `If-None-Match` and `If-Match` with 304/412 branches (SEC_05–10, SEC_21–24). Two rows actually **understate** coverage: `BLK_01` fails if the server omits `bulkId` or `location` on created ops ([A7:77–92](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A7_BulkOperationsSpec.groovy#L77)), and `USR_01` asserts `meta.location == Location` ([A3:62](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A3_UserCrudSpec.groovy#L62)) — the matrix called the first a Partial and buried the second in a note.

## A stack of RFC 7644 duties sits outside the matrix entirely

A normative-keyword sweep of RFC 7644 §§2–7.5.2 found at least fifteen — the audit enumerates 22 — requirements with **no matrix row**, which means they are invisible to anyone using the matrix as a gap tracker even where a test incidentally exercises them ([RFC 7644 coverage audit §Q2](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/01_rfc7644_protocol_coverage.md)). The omissions cluster into structural PATCH rules that the suite's own payload builder makes untestable as written (exactly one `op` member, `value` required for `add`, `remove` without `path` → 400 `noTarget`, the `primary:true` auto-unset rule, the 204 response branch, and the mandatory 200 when an `attributes` parameter is present), bulk duties (`bulkId` REQUIRED on POST, per-op `version`, and the MUST continue performing later operations after a partial failure — BLK_12–14 only show failing ops, never failure-then-success), and durability duties (`If-Match` on DELETE, which Table 8 lists as applicable and §3.6's example demonstrates, but which no test attempts). On the root query side, RFC §3.4.2.1's `meta.resourceType` scoping and §3.12's `tooMany` are named Gaps but the loadable `filterMaxResults` was never read by any spec; §3.8's UTF-8 and default-media-type rules are unobservable because every request sends both `Content-Type` and `Accept`; and §3.12's requirement that 401/403 responses carry a JSON error body is untested even though SEC_01/02/15 check those statuses. The newest normative surface is absent outright: **RFC 9865** (Oct 2025) adds cursor pagination (`cursor`/`nextCursor`) and **RFC 9967** (May 2026) adds asynchronous requests while updating 7643/7644, neither mentioned in matrix or suite ([RFC 9865](https://www.rfc-editor.org/rfc/rfc9865.html), [RFC 9967](https://datatracker.ietf.org/doc/rfc9967/)). The same sweep exposes hygiene gaps that matter the moment the suite points at a compliant-but-minimal server: PATCH is "an OPTIONAL server function" yet all 21 A4 tests run unconditionally, bulk's optional flag is never consulted, filtering is assumed by A3/A5/A6/A7/A9 without a gate, and `isEtagSupported()` is dead code while SEC_08/SEC_23/GRP_17 hard-require ETags ([ScimBaseSpec.groovy:58–84](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/base/ScimBaseSpec.groovy#L58)).

## RFC 7643 coverage checks schema spelling, not schema semantics

The RFC 7643 half is directionally right at section granularity but materially weaker than its labels: four citation errors, one mislabeled inconsistency reference, and multiple statuses that need downgrading ([RFC 7643 coverage audit](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/02_rfc7643_schema_coverage.md)). The centerpiece is A2's `validateAttributeCharacteristics` helper ([A2:419–471](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A2_SchemaValidationSpec.groovy#L419)), which validates enum membership **only when a characteristic is present** and never enforces any §2.2 default, `caseExact`, `canonicalValues`, `description`, characteristic/type applicability, or `referenceTypes` content. So "§2.2 Covered" means "the enum members a server chose to publish are spelled correctly," not "the schema conforms"; and if a schema omits `attributes` entirely, validation is skipped. The `password` row should fall from Covered to **Partial** because every assertion is inside `if (passwordAttr != null)` — a server that never publishes `password` passes with a note ([A2:97–107](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/specs/A2_SchemaValidationSpec.groovy#L97)) — and the `externalId` row cites USR_02/USR_05, which never set or read `externalId`; real coverage is PAT_01, GRP_01, and GRP_04. The reference-integrity tests (GRP_13/GRP_15) assert 400/404 for dangling members when RFC 7643 §2.3.7 says enforcing referential integrity is a provider **MAY** ([rfc7643.txt:579–581](https://www.rfc-editor.org/rfc/rfc7643.txt)) — a MAY promoted to MUST that fails compliant servers. Erratum collisions have also outdated justifications: erratum 5368 (Verified 2025-10-28) makes Group `displayName.required` true, while A2 still accepts `false` citing the pre-erratum JSON; errata 8417 and 8475 (both Verified) require Schema representations to carry `schemas`+`meta` and ResourceType `name`/`endpoint` to be server-unique and case-exact, none of which is tested ([RFC 7643 errata](https://www.rfc-editor.org/errata/rfc7643)).

## Where the coverage claims break down, and how much to trust a green run

The artifacts fail in two distinct ways: specific misstatements in the matrix, and a pass/fail signal that cannot carry the weight of "Covered." The specific corrections are concentrated and easy to apply: the matrix's **§3.5.2.2 and §3.5.2.3 are swapped** (RFC: .2 is Remove, .3 is Replace) and the test comments repeat the inversion across PAT_02/03/05/11/12/13 and PAT_04/07/21; the heading "§3.1 Creating Resources" should be **§3.3** because §3.1 is Background; the `Content-Location` requirement is cited to RFC 7644 but exists only in RFC 7643 §3.1 (`meta.location` "MUST be the same as the 'Content-Location' HTTP response header"), a string that appears zero times in RFC 7644; the §2 note pointing at SEC_09/SEC_12 for 403 tolerance is wrong (the actual tolerant tests are SEC_03, PAT_09, USR_06); the §3.7 claim "`bulkId` echo not asserted" is wrong (BLK_01 fails without it); the `externalId` row cites tests that never touch the attribute; and the matrix's own complaint about non-existent `§3.4.2.2.x` subsections is not supported by the current tree ([RFC 7644 coverage audit §Q1](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/01_rfc7644_protocol_coverage.md)). The tracker repeats and amplifies these errors: **stale line references throughout A3/A4/A5/A6**, PUT labeled "§3.3" when it is §3.5.1, uniqueness labeled "§3.3.1" when §3.3.1 is Resource Types, and A2 marked 100% while claiming `phoneNumbers` validation that does not exist.

Four test comments quote sentences that **do not exist in RFC 7644** — PAG_04's out-of-bounds mandate, FLT_33's root-search 501 claim, SRT_05's ignore-unsupported-`sortBy` clause, and A1's "Service providers MUST provide Schema definitions for ServiceProviderConfig, ResourceType, and Schema itself" (the nearest text is an example in RFC 7643 §8.7.2) — while FLT_35 is a defensible paraphrase, FLT_36 attributes a query-parameter rule to attribute names, PAT_17 asserts a case-insensitive `op` with no RFC basis, and BLK_03 downgrades a MUST (413) to MAY ([quote verification](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/01_rfc7644_protocol_coverage.md), [Q3](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/01_rfc7644_protocol_coverage.md)). The trustworthiness audit frames the pattern precisely: comments describe the intended strict check; the executable assertion is looser — conditional, alternative-set, or deviation-logged ([Suite trustworthiness audit](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/04_suite_trustworthiness_audit.md)). Across 186 verified feature methods, **21 `scimType` checks are soft** (omission is RFC-legal, but keyword-specific tests then prove nothing), FLT_13/14 projection leaks, SRT_02's descending bug, A1's non-405 tolerance, PAT_18/19 and BLK_18/19 acceptance branches, and SEC_19/20/24 alternatives each print a deviation and pass; deviations are stdout-only and **suppressed entirely when capture mode is on**, so a library consumer can get a green run with zero visibility of tolerated non-compliance ([ScimOutput.groovy:5–15](file:///Users/eduardpal/work/scim2/scim-validator/src/main/groovy/de/palsoftware/scim/validator/base/ScimOutput.groovy#L5)). Added false-fails — a compliant server can fail — come from ungated PATCH/bulk/ETag/`/.search`/enterprise-schema requirements, the `/Me` 501-only assertion, Bearer-only auth assumptions, and A2's unguarded mutability loop that rejects omitted `mutability` although §2.2 defines a default. The audit found no CI logs or surefire reports in the repo, so the tracker's 99% remains unsubstantiated by any artifact; and because `SCIM_SPEC_COVERAGE.md` is untracked, its errors are outside review history ([Suite trustworthiness audit §Q1](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/04_suite_trustworthiness_audit.md)). None of this was validated by execution: the notes are static code analysis, and the documented deviations name api.scim.dev but store no run metadata.

## The industry bar, and what to fix first

There is **no formal SCIM certification** to compare against: every public tool self-describes as a practical interoperability check, and the closest to a coverage claim (WSO2's PDF percentages) is unverified, while the tooling ecosystem's own disclaimer is explicit — SCIM Verify says passing "does not prove complete compliance or production readiness" ([scim.dev/verify/about](https://scim.dev/verify/about)). What the field actually documents as failures is telling: Traxion's study of 40–50 SCIM APIs lists missing configuration endpoints, broken PATCH semantics, malformed error responses, wrong `totalResults`, and casing mangling, and notes most Azure AD-targeted APIs skipped the mandatory discovery endpoints entirely ([Traxion](https://www.traxion.com/blog/the-10-most-common-pitfalls-for-scim-2-0-compliant-api-implementations)); Microsoft still ships non-compliant PATCH behind the `aadOptscim062020` flag with status "TBD" ([Microsoft Learn](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/application-provisioning-config-problem-scim-compatibility)); and the emerging interop profile restricts clients to `eq`/`and`, mandates a PATCH `path`, prohibits `If-Match`/ETag use, and calls bulk optional ([draft-zollner-scim-interop-profile-01](https://datatracker.ietf.org/doc/draft-zollner-scim-interop-profile/01/)). Real servers skip bulk, sort, `/Me`, and ETags outright ([Posit Connect SCIM reference](https://docs.posit.co/connect/admin/appendix/scim/api-reference.html)). The suite therefore over-invests relative to client demand in exactly the optional features it hard-requires, and under-invests in the areas the literature says break interop: error semantics, `totalResults` correctness on filtered queries, PATCH dialect breadth, discovery completeness, and `scim+json` handling — several of which are precisely where its assertions are soft. One more calibration point: the default target api.scim.dev is run by Limosa, the same organization that publishes the scimverify tool, so passing there demonstrates the suite runs end-to-end, not that its expectations match third-party norms ([api.scim.dev context](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/03_industry_conformance_practice.md)).

The remediation order that converts the suite from "green unless visibly wrong" into usable evidence is already scoped by the trustworthiness audit ([§Q3 prioritized list](file:///Users/eduardpal/work/scim2/scim-validator/research_notes/SCIM%20validator%20spec%20coverage/04_suite_trustworthiness_audit.md)). P0 items are mutually reinforcing and all low-to-medium effort: a `scim.strictScimType` mode that fails (or records structurally) on keyword omission; capability gating for PATCH, bulk, ETag, `/.search`, and the Enterprise extension, with a **fail-loud** SPC load that distinguishes "unknown" from "false"; a machine-readable deviation sink that also fixes capture-mode suppression; `/Me` accepting 200/308/501; and pagination asserting `itemsPerPage <= count` rather than equality. P1 items fix multiplying false-passes across A3/A4/A5: nullable mutability in A2, exact result sets with a per-class `PREFIX`, routing all error checks through `assertScimError`, rejecting NEG_19's 201-on-unknown-schema branch, enforcing 413+body for bulk limits, and discovering the auth scheme instead of asserting Bearer. The artifacts themselves should be regenerated rather than edited: a normative-keyword sweep produced the missing-row lists, so the next matrix should be rebuilt from that sweep, with corrected section numbers, retracted fabricated quotes, verified test line references, and a stated scope ("RFC 7643/7644 as published, not as updated by RFC 9865/9967").

## Conclusion

The most valuable part of the current artifacts is the gap list, not the Covered count: the audit's corrections move the trustworthy number of rows toward more Partial and more Gap, but they also enlarge the requirement surface by dozens of rows the matrix never tracked. The strategic insight is that the suite's credibility problem is not lack of tests — 186 methods cover the protocol core thoroughly — it is that soft assertions and ungated optional features make the pass signal ambiguous in both directions, failing compliant servers on optional features while passing non-compliant servers on mandatory error keywords. A strict mode, capability gating, and structured deviations would resolve both at once and let the Covered/Partial/Gap labels mean what readers assume they mean. Until then, treat any claimed coverage percentage as a hypothesis list to verify per target: results are target-dependent by construction, deviations differ per server, and no run metadata or CI history exists in the repo to calibrate them.
